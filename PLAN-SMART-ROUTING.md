# AI Code — Tier 2: Smart Routing & Context

Depends on: Tier 1 complete (TUI, dashboard, agent lifecycle all functional).

Tier 2 makes the system intelligent about *which* model does *what* work, *how much* context it gets, and *whether* tasks can overlap.

---

## Current State

- **Context engine**: file tree paths only — never reads file contents. No architecture/conventions docs. No relevant-file selection per task. No `context enrich`.
- **Provider health**: `lastError`/`lastFailedAt` stored but never consulted during routing. No circuit breaker.
- **Model capabilities**: every model gets `['planning','coding','review','repair']`. No differentiation.
- **Parallel execution**: CLI runs tasks sequentially. `execute` is a single blocking call.

## Milestone 1 — Context Engine (E)

### 1a. File content in context

Currently `buildContext` sends file paths only. The agent gets a list of filenames but no code.

Add relevant-file selection:

```
src/context.mjs  — relevantFiles(project, task) → file paths ranked by relevance
```

Heuristics (no LLM needed):
- Files mentioned in the task title (fuzzy match against filenames)
- Files changed in recent Git history related to the task's keywords
- Entry points (index.*, main.*, app.*)
- Test files adjacent to mentioned source files
- Config files (package.json, tsconfig, etc.)

Cap: include actual contents for top N files (configurable, default 15), paths only for the rest. Total content budget: configurable token limit (default 50K tokens).

### 1b. Architecture and conventions docs

```
.ai-code/context/
  architecture.md    — generated by `context enrich`
  conventions.md     — generated by `context enrich`
  dependencies.json  — extracted deterministically from manifests
```

**dependencies.json** — deterministic, no LLM:
- Parse package.json (deps + devDeps), pyproject.toml, go.mod, Cargo.toml
- Record: name, version, dev-only flag
- Run at `context init`

**architecture.md** and **conventions.md** — LLM-generated:
- New command: `ai-code context enrich`
- Reads the file tree + key source files + existing context
- Asks the selected planner-role model to produce structured docs
- Stores result in `.ai-code/context/`
- Idempotent: re-running updates rather than appends
- These docs are included in every agent prompt as project context

### 1c. Per-task context assembly

```
src/context.mjs  — buildTaskContext(project, task) replaces buildContext
```

Assembly order:
1. Project-level context (architecture, conventions, commands)
2. Task-specific relevant files (from 1a)
3. Approved plan (if exists)
4. Review findings (if in repair stage)
5. Previous run summary (if retrying)

Token budget enforcement:
- Each section has a max allocation
- If total exceeds budget, trim file contents (keep most relevant), then trim architecture doc
- Log actual token usage per context assembly for observability

### 1d. Context efficiency tracking

Add to run records:
```
context_tokens    — tokens used for context (vs model output)
relevant_files    — count of files included
context_budget    — configured budget for this run
```

Feeds into the observability dashboard (Tier 3) and immediate usage view.

## Milestone 2 — Provider Health in Routing (F)

### 2a. Circuit breaker

```
src/service.mjs  — eligible() consults provider health before scoring
```

Health states:
```
HEALTHY          — normal operation
DEGRADED         — recent failures, still eligible but penalised
OPEN             — too many failures, temporarily excluded from routing
```

Transition logic:
- 1 failure in 5 minutes → DEGRADED (score penalty: -30%)
- 3 failures in 5 minutes → OPEN (excluded from routing)
- OPEN → DEGRADED after cooldown period (default 2 minutes)
- DEGRADED → HEALTHY after 3 consecutive successes
- All thresholds configurable in routing.json

### 2b. Health-aware scoring

Update `eligible()` scoring formula:

```
current:  quality * qWeight + speed * sWeight - cost * cWeight + preference
proposed: quality * qWeight + speed * sWeight - cost * cWeight + preference + health
```

Where `health`:
- HEALTHY: +0
- DEGRADED: -30% of total score
- OPEN: excluded entirely

### 2c. Provider health API

```
GET /api/providers/:id/health  — returns current health state, failure history, cooldown status
```

Dashboard and TUI show health state on provider cards:
- Green dot: HEALTHY
- Yellow dot: DEGRADED (with "3 failures in last 5m" tooltip)
- Red dot: OPEN (with "circuit open, cooldown 1m 30s remaining")

### 2d. Failure classification improvements

Current `classify()` in agents.mjs catches: RATE_LIMIT, USAGE_LIMIT, AUTH_FAILURE, TIMEOUT, AGENT_FAILURE.

Add:
- `PROVIDER_DOWN` — connection refused, DNS failure, 5xx responses
- `MODEL_UNAVAILABLE` — model ID not found, model deprecated
- `CONTEXT_TOO_LARGE` — token limit exceeded

Different failure types should trigger different responses:
- AUTH_FAILURE → mark provider OPEN immediately (won't self-heal)
- RATE_LIMIT → short cooldown (30s), then retry same provider
- USAGE_LIMIT → mark provider OPEN for longer (10 minutes)
- PROVIDER_DOWN → standard circuit breaker logic
- TIMEOUT → count toward circuit breaker
- AGENT_FAILURE → count toward circuit breaker
- CONTEXT_TOO_LARGE → don't penalise provider; reduce context and retry

## Milestone 3 — Meaningful Model Capabilities (G)

### 3a. Capability schema

Replace the flat `['planning','coding','review','repair']` list with structured capabilities:

```json
{
  "roles": ["planning", "coding", "review", "repair"],
  "contextLength": 200000,
  "reasoning": "strong",
  "speed": "moderate",
  "toolUse": true,
  "vision": false,
  "streaming": true
}
```

Fields:
- `roles` — which workflow roles this model can fill (same as current, but now actually differentiated)
- `contextLength` — actual context window (already stored, not used in routing)
- `reasoning` — "basic" | "moderate" | "strong" | "frontier"
- `speed` — "slow" | "moderate" | "fast" | "instant"
- `toolUse` — boolean, required for implementer/repair
- `vision` — boolean, future use
- `streaming` — boolean, required for live event display

### 3b. Capability-aware routing

Update `eligible()`:
- Planner requires `reasoning: "strong"` or higher
- Implementer requires `toolUse: true`
- Reviewer requires `reasoning: "moderate"` or higher
- Repair requires `toolUse: true`

Context length check:
- If estimated task context exceeds model's `contextLength`, skip that model
- Log when a model is skipped for context reasons

### 3c. Model catalog updates

Update the hardcoded catalogs in cli.mjs (and eventually the dynamic provider system in Tier 3):

```
Claude Opus 5:     reasoning=frontier, speed=moderate, toolUse=true
Claude Sonnet 5:   reasoning=strong,   speed=fast,     toolUse=true
Claude Haiku 4.5:  reasoning=moderate, speed=instant,  toolUse=true
DeepSeek V4 Pro:   reasoning=strong,   speed=moderate, toolUse=true
DeepSeek Flash:    reasoning=moderate, speed=instant,  toolUse=true
```

### 3d. Migration

- Add new columns to models table (reasoning, tool_use, vision, streaming)
- Migrate existing capabilities array to structured format
- Backward compatible: old format still works, new fields default to permissive values

## Milestone 4 — Parallel Execution (H)

### 4a. Independent task execution

Currently `execute` is a blocking call that runs implement → test → review sequentially. Two tasks can't run at the same time from the CLI.

Split `execute` into independent steps:
```
POST /api/tasks/:id/implement  — starts implementation, returns immediately
POST /api/tasks/:id/test       — runs tests (after implementation completes)
POST /api/tasks/:id/review     — runs review (after tests pass)
```

Each step is a background job. The harness polls or SSE-streams progress.

### 4b. Background job runner

```
src/runner.mjs  — simple job queue, max concurrency configurable
```

- Jobs are persisted as runs in SQLite (already the case)
- Runner picks up pending work and executes it
- Max concurrent agents: configurable (default 2 — one per provider)
- Worktree isolation already guarantees no cross-contamination

### 4c. CLI support

```
ai-code task execute <id> --background    — starts execution, returns immediately
ai-code task status <id>                   — shows current state + active run
ai-code tasks active                       — lists all tasks with running agents
```

The TUI already handles this naturally (SSE updates).

### 4d. Concurrency-safe provider selection

When two tasks run simultaneously, they might both select the same provider. This is fine for API-based providers (DeepSeek), but Claude Code CLI might have issues with concurrent sessions.

- Add `maxConcurrency` to provider config (default: 2 for API, 1 for Claude Code CLI)
- `select()` checks current running runs per provider before selecting
- If at max concurrency, skip to next eligible provider

## Implementation notes

Shipped. This section records where the build departed from the plan above, and
why. Everything not listed was built as specified.

### Build order

Rebuilt as: readable-style rewrite of the core `src/*.mjs` files → Phase B →
Phase C → Phase A → Phase D. The rewrite touched every file the other phases
touch, so doing it first meant the rest was written in the target style once.
Phase D came last because it depends on the lease work done in the rewrite.

### Deviations

| Plan says | Built | Why |
|---|---|---|
| `capabilities` becomes an object | Kept the flat roles array, added `reasoning` / `tool_use` / `vision` / `streaming` columns beside it | `.includes()` is called on the parsed array in three places and `.join()` in one; an object breaks all four |
| Health state lives in provider config | A dedicated `provider_health` table | `updateProvider` rewrites the whole config blob from a snapshot, so a health write and a config edit would clobber each other |
| Failure window stored as a list of timestamps | Counted from the `runs` table inside the window | `runs` is already the record of every attempt, and it is correct across processes and after a restart |
| Context-length check lives in `eligible()` | One check in `runRole`, after assembly | The prompt size is not known until the context is assembled; a pre-filter could only guess. An over-long prompt excludes the *model*, not its provider |
| `speed_tier` column | Not added | No gate consumes it, and the numeric `speed` already exists for scoring |
| `ai-code tasks active` | `ai-code task active` | The CLI has a singular `task` namespace and no plural one |
| `context enrich` under a deterministic bootstrap | A separate opt-in command; the invariant was amended to distinguish the two | `docs/ARCHITECTURE.md` states the bootstrap needs no LLM, and it still does not |
| A cancelled run's lease is the cancel channel | A `cancel_requested` flag on the task as well | A cancel landing between two steps, or during the test command, holds no lease and would otherwise be forgotten |
| *(not in the plan)* | `run_leases` and a lease-aware `reapStaleRuns()` | Every CLI invocation opened the store and marked every in-flight run `interrupted`, corrupting live runs |
| *(not in the plan)* | `AI_CODE_ALLOW_MOCK=1` on the server | Without it the server cannot be driven end to end in a test, since mock providers are excluded from production routing by design |
| *(not in the plan)* | A cap on the file tree in the assembled context | The tree grows with the repository, not the task, so an unbounded one made the token budget unenforceable |

### Three gaps found during the build, and closed

Each was fixed after the tier's tests were green, each with a test that fails
against the code before the fix.

| Gap | Fix |
|---|---|
| `price()` keyed peak/off-peak off the literal provider id `deepseek-claude-code`, so renaming the provider silently repriced every run at off-peak | Keyed off the model's own rates: a model carrying `peakInputCostPerMTok` has a peak tier, one without it does not. The rates are the fact; the id was a proxy for it |
| `web/views/routing.mjs` wrote `timeoutMs` while the service reads `timeout` in seconds, so the dashboard's timeout field was inert | The field writes `timeout` in seconds, matching `src/policy.mjs` and the label |
| The per-provider concurrency gate counted `service.active` in memory, so it only saw this process's runs | Counted from the live leases via `Store.countRunningByProvider()`, which is the one record every process writes. A run held by the dashboard now counts against a CLI-started job and vice versa |

The lease count carries the staleness cutoff for the same reason `reapStaleRuns`
does: a lease whose owner died must not hold a provider slot forever.
